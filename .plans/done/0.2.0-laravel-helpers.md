# 0.2.0 — Laravel's helpers, and references by full number

**Status:** Done. Released as `v0.2.0` and closed on 2026-11-25; every task's evidence is in [0.2.0-progress.md](0.2.0-progress.md). Approved by the owner on 2026-11-25. Written 2026-11-25 from two read-only audits that day (the service's public API against the package; the package's code against Laravel's helpers), the owner's answers, and the owner's decision on references the same day.
**Branch:** `main` (no branches, no PRs)

## Goal

The package matches the service again and is written the way the service now is: Laravel's helpers and built-in solutions wherever Laravel has one, kept that way by Rector and an arch test, as in the service's commit `24b9852`. Corrective and replacing invoices refer to any original by its full number, so they also work for invoices an app issued from another system before the service.

**Done when:**

1. `composer test` is green, including `rector --dry-run` (no change left) and the arch rule that forbids PHP's functions with a Laravel twin. `composer test:mutate` is at least 90%.
2. `correcting()` and `replacing()` refer to every original by its full `invoice_number` and `issue_date`, whether it was issued through the service or by another system. Through `Verifactu::fake()`, an R1 correcting an invoice from another system is issued.
3. A new Laravel app that requires the package and runs Boost's install gets the package's guideline and skill. Both describe 0.2.0 exactly: every class, method, argument, config key, command and event they name exists in `src/`; every code example is written the package's way (Laravel's helpers, collections, no needless braces); nothing they say contradicts the README or the service's Laravel guide.
4. `v0.2.0` is tagged and on Packagist, and `composer require vlec/laravel-verifactu:^0.2` installs it in a new Laravel app.

## Decisions

1. **Mirror the service's tooling** (owner, 2026-11-25: "non negotiable").
    - Use the service's `rector.php`: the same function-to-helper map, PHP sets, code-quality/dead-code/type sets, Laravel sets and `withComposerBased(laravel: true)`. That includes `DispatchToHelperFunctionsRector` (`X::dispatch()` → `dispatch(new X)`, owner).
    - Paths: `src`, `config`, `database`, `workbench` and `tests`.
    - Skip only what breaks the package: the two rules above where they break, and the crashing file if the current Rector still crashes on it.
    - Copy the service's arch rule for `Vlec\Verifactu` and `Workbench`.
    - `composer test` runs `rector --dry-run`, because local `composer test` is the package's gate. `composer lint` runs Rector, then Pint.
2. **Latest Laravel only** (owner, 2026-11-25: "If Laravel 13.43 is needed so be it… there is no need to worry about older versions"). The floor becomes the 13.x installed after `composer update` (13.44 today), with Testbench to match.
3. **`InvoiceData::taxLines()` returns `Collection<int, TaxLine>`** (owner, 2026-11-25: "we change it now"). So do the package's other own methods whose callers wrap them:
    - `InstallCommand::configKeysNotOnTheirOwnLine()`, `columnDefinitions()` and `columnDrops()`
    - `InvoiceListQuery::sorts()`, `names()` and `includes()`
    - `ApplyInvoiceBatch::items()`
4. **Retries use Laravel's backoff.**
    - `RetriesThroughTheQueue` drops `$releaseDelays` and `releaseDelay()` for `public array $backoff = [10, 30, 60, 300]` and `$this->releaseUsingBackoff()` (Laravel 13.43+).
    - A `Retry-After` from the service still wins.
    - The public `$releaseDelays` property goes. That's a breaking change, named in the upgrade notes.
5. **References go by full number** (owner, 2026-11-25). Corrective (R1–R5) and replacing (F3) invoices may refer to any invoice, issued through the service or by another system before it, as long as the number sequence continues. AEAT only needs the full number and the issue date.
    - `reference()` always sends `invoice_number`, from `config('verifactu.columns.invoice_number')`, with `issue_date` as today. It never sends `number`, so it never sends both.
    - For an invoice the service issued, nothing changes: the service links it as it did by `number`.
    - An invoice with neither a number nor an issue date (not issued yet) keeps today's behaviour: the reference goes without them and the service refuses it.
    - The R5 check in `correcting()` (`$original->toVerifactu()->isSimplified()`) stays.
    - The `number` column stays and now just holds "the number within the series and year, such as 42".
    - No new config. The package doesn't check the value; the service decides.
6. **`0.2.0`**, not `0.1.2`: references change, and `taxLines()`, `$releaseDelays` and the Laravel floor are breaking changes.
7. **The Boost guideline and skill are part of the public API.** They're what an app's AI agent reads, so every change to the public API, or to the way the package wants app code written, updates them in the same release. They're checked against `src/` and the README, and installed into a scratch app, before the release.
8. **A model's lines are a collection** (owner, 2026-11-25). The mixed-order example is written once, in the workbench model (the tested code), and copied as it is into the README and the Boost skill:

    ```php
    public function toVerifactu(): InvoiceData
    {
        return InvoiceData::make("Order $this->id")
            ->to(Recipient::spanish($this->customer_tax_id, $this->customer_name))
            ->lines(collect([
                TaxLine::exempt($this->exempt_cents),
                TaxLine::vat($this->taxable_cents, rate: 21),
            ])->reject(fn (TaxLine $line): bool => $line->baseCents === 0));
    }
    ```

    The `$lines[] =` blocks go from `workbench/app/Models/Invoice.php:41`, `README.md:146` and the skill's `SKILL.md:54`.
