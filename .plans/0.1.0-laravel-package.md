## Goal

Any of the company's Laravel apps plugs into the service the same way. It runs `composer require vlec/laravel-verifactu`, then `php artisan verifactu:install`, and adds three `.env` keys. From then on its own invoice model issues invoices (one at a time or in a batch), fixes a record, cancels an invoice and checks a customer's tax ID. Its invoice table always holds the latest status, kept up to date by webhooks. The app's items stay in the app: the package turns them into the tax lines AEAT needs, VAT and exempt mixed in one invoice from the first version (the first app needs that in early 2027).

What an app writes:

```php
class Invoice extends Model implements VerifactuInvoice
{
    use IssuesVerifactuInvoices;

    public function toVerifactu(): InvoiceData
    {
        return InvoiceData::make("Order {$this->id}")
            ->to(Recipient::spanish($this->customer_tax_id, $this->customer_name))
            ->lines($this->items->map(fn (Item $item): TaxLine => $item->is_exempt
                ? TaxLine::exempt($item->total_cents)
                : TaxLine::vat($item->subtotal_cents, rate: 21)));
    }
}

$invoice->sendToVerifactu();                      // queued, after commit
Verifactu::sendBatch($invoices);                  // one batch, queued
$invoice->correctOnVerifactu('Spanish course, B2'); // fixes the record's description
$invoice->cancelOnVerifactu();                    // issued by mistake

Event::listen(InvoiceIssued::class, SendInvoicePdf::class);   // number, date and QR are stored
Event::listen(InvoiceRejected::class, NotifyAccounts::class);
```

## Decisions

1. **Laravel's official skeleton** (owner, 2026-11-19). `laravel package laravel-verifactu` creates the package in `/Volumes/Storage/Projects/Laravel/laravel-verifactu`. It brings Pest 5, Testbench 11, Larastan, Pint, 100% type coverage, a workbench app, `AGENTS.md` and agent skills: `package-scaffold`, `package-testing`, `package-release`, `package-compatibility` and `package-generate-skill`. The service provider uses Laravel's own package methods (`mergeConfigFrom`, `publishes`, `publishesMigrations`, `loadRoutesFrom`, `commands`, `AboutCommand::add`). Spatie's `laravel-package-tools` would add a dependency to save about ten lines. Spatie's coding guidelines (`spatie-laravel-php`) still apply to every file.
2. **Home and name** (owner, 2026-11-19):
    - Composer name `vlec/laravel-verifactu`, PHP namespace `Vlec\Verifactu`, MIT licence.
    - Public repository `github.com/virginialyons/laravel-verifactu`, unadvertised: not meant for anyone outside the company. It never names the company's apps.
    - Its own folder next to the service, `/Volumes/Storage/Projects/Laravel/laravel-verifactu`, with its own repository. That is how Laravel ships Cashier and Horizon and how Spatie ships every package. Packagist needs the package at the root of its own repository, and the service's code stays private. The two are tied by the API (`public/openapi/v1.json` and the copied examples, Decision 19), not by shared code. This plan and its tracker move into the package's `.plans/` in T1 (Decision 20).
    - PHP `^8.4` and Laravel `^13` only.
    - First tag `0.1.0` when Done-when 1 holds. `1.0.0` when the second app uses it in production (the service's M9).
3. **No CI on push** (owner, 2026-11-19: "This is not meant for public use"). The skeleton's `tests.yml` becomes `workflow_dispatch` only, on Ubuntu, PHP 8.4 and 8.5 × Laravel 13. It loses the Windows, PHP 8.3 and Laravel 12 rows. Local `composer test` is the gate, as in the service. `update-changelog.yml` stays: a GitHub release writes `CHANGELOG.md`.
4. **The model describes the sale; the package does the rest.** The app's model implements `VerifactuInvoice` and uses the `IssuesVerifactuInvoices` trait; the app writes one method, `toVerifactu(): InvoiceData`. The contract also lists the trait's public methods, as Laravel's `Authenticatable` contract lists its trait's, so jobs and events can type the model by it (T4). `InvoiceData` is a small immutable builder:
    - `make($description)`
    - `->to(Recipient)`: `Recipient::spanish($taxId, $name)` or `Recipient::foreign($name, $countryCode, ForeignIdType, $id)`
    - `->lines(iterable<TaxLine>)`
    - `->simplified()`: F2, no recipient
    - `->replacing(...$simplifiedInvoices)`: F3
    - `->correcting($original)`: a corrective invoice for the difference, R1, or R5 when the original is simplified

    Nothing in it is an AEAT field name. It turns into the API body and nothing else (no HTTP).

    `->taxLines()` gives the grouped lines back (a getter separate from the `->lines()` setter). `->correcting()` and `->replacing()` take the app's issued models (`Model&VerifactuInvoice`) and read their `number` and `issue_date` columns; R5 is chosen when the original's own `toVerifactu()` is simplified. An original not yet issued throws.

    The `external_reference` is always derived from the model's key (`invoice:{key}`), never chosen by the app, so the package can always find the model from it (DEX-002).
5. **Money is whole cents, as in both apps and Stripe.** `TaxLine::vat($baseCents, rate: 21)` and `TaxLine::exempt($baseCents)`; the reason defaults to `config('verifactu.exemption_reason')`, `E1`.
    - The package groups lines with the same rate, or the same exemption reason, by adding their bases. The tax is worked out once per grouped line: base × rate / 100, rounded half up to the cent with PHP 8.4's `BcMath\Number` (`ext-bcmath`), never a float. The service accepts that within 0.02.
    - The total is the sum of bases and taxes.
    - No lines, or more than 12 grouped lines, throws before any call (the API takes 1 to 12).
    - `InvoiceData::taxLines()` gives the grouped lines back, so the app prints exactly what AEAT receives.
    - Negative bases are allowed (a corrective invoice for the difference).
6. **Issuing runs in the background** (owner, 2026-11-19).
    - `sendToVerifactu()` dispatches `IssueInvoice` after the transaction commits, unique per model.
    - The `Idempotency-Key` is the model's reference plus a UUID made when the job is dispatched, kept across that job's retries (owner, 2026-11-19, after the T4 review). The service replays a `4xx` for 24 hours under a key, and refuses the same key with another body, so a body hash or the id alone would block a re-send after a fix. A second invoice for the sale is stopped by the unique `external_reference` (`409`, which the job turns into storing the existing invoice).
    - The job owns its retries (DEX-001). It calls the client with automatic retries off, so each attempt makes one request.
    - What each answer does:
        - `201` stores the answer and fires `InvoiceIssued`.
        - `409 external_reference_already_used` stores the invoice already issued, found by its reference.
        - A retryable answer (`VerifactuException::isRetryable()`: no answer, `5xx`, `429`, `503`, `409 idempotency_key_in_progress`) releases the job for `retryAfter` seconds, or the backoff. The same key is used.
        - Any other `4xx` fires `InvoiceNotIssued` with the error and fails the job.
    - How (T4): `$maxExceptions = 1`, so any exception the job doesn't release fails it at once, and `failed()` fires `InvoiceNotIssued`; releases wait 10, 30, 60, then 300 s without a `Retry-After`; `retryUntil()` is 24 hours, the time the service replays a key. A model already on Verifactu sends nothing, and `failed()` fires nothing for one (a listener that failed after the answer). The unique lock lasts 25 hours. `InvoiceNotIssued` carries `errorCode` and `message`, not the exception, so queued listeners can serialize it. The trait keeps an app's own cast of the issue-date column.
7. **Batches** (owner, 2026-11-19: "issue a single invoice or an invoice batch").
    - `Verifactu::sendBatch(iterable $invoices)` dispatches `SendInvoiceBatch`. It posts `/invoice-batches` with a key made from the references and the body, and stores the batch's UUID in a package table, `verifactu_invoice_batches` (uuid, status, timestamps), published with `publishesMigrations`.
    - When the batch is done (webhook `invoice_batch.completed`, or `refresh-pending`), `ApplyInvoiceBatch` reads `/items` 100 at a time and matches each item to a model by `external_reference`. An issued item is stored and fires `InvoiceIssued`, a failed one fires `InvoiceNotIssued`. Then the batch fires `InvoiceBatchCompleted` with its totals.
    - The table is what lets a missed completion webhook be found again. The app's own table gets no batch column.
8. **The app's table holds the latest status, from webhooks** (owner: re-read, don't apply the payload).
    - The package's route `POST /verifactu/webhook` (path configurable) lives outside the `web` group, so there is no CSRF exemption to add, no session and no cookies.
    - Middleware `VerifyWebhookSignature` checks `t`/`v1` over the raw body with `hash_equals()` and the 300 s limit, as Cashier's middleware does. It answers `403` (final) when the signature fails.
    - For `invoices.updated`, each invoice found in the model table by `verifactu_uuid` gets a `RefreshInvoice` job. That job reads `GET /invoices/{uuid}` and stores it. There is no second lookup by reference (DEX-003). A job that crashed after a `201` is healed by its own retry with the same key. A batch invoice not yet stored is filled when the batch is applied.
    - `RefreshInvoice` is `ShouldBeUniqueUntilProcessing`: a webhook that arrives while it runs queues a fresh read instead of being dropped. Its `WithoutOverlapping` middleware (per invoice, released after 5 s, expiring after 60 s) makes that read wait for the running one, even on several workers (T5 review), so an older read never saves over a newer one. Webhooks arriving out of order no longer matter, because the last read wins.
    - Unknown invoices (another app or environment) are skipped. `ping` answers `200`. The answer is `200` once the jobs are queued, and a `5xx` if queueing fails, so the service retries.
9. **Columns, the bare minimum** (brief):
    - `verifactu_uuid` (unique), `verifactu_status` (indexed, cast to the package's `InvoiceStatus` enum), the app's own number and issue-date columns (filled from the answer), `verifactu_url` and `qr_code`.
    - `verifactu_number` (owner, 2026-11-19): the answer's bare `number` ("42"), next to the printed `invoice_number` ("FACT42"). A corrective invoice or an F3 names the earlier invoice by that bare number and its issue date, as the API's correction guide says; `invoice_number` is only for invoices issued by another system. The app never uses it.
    - `config('verifactu.columns')` maps each one to a column name. The trait's `initializeIssuesVerifactuInvoices()` merges the casts with `mergeCasts()`.
    - Before the first answer the status is `null`. AEAT's error stays in the service and arrives with `InvoiceRejected`.
10. **Fixing and cancelling call the service directly, as Stripe and Cashier do** (owner, 2026-11-19, after research). Stripe's refund and void calls and Cashier's `refund()`, `cancel()` and `cancelNow()` are direct calls. The answer isn't final (a refund comes back `pending`), and webhooks bring the outcome. Adyen, Paddle and Mollie work the same way. The side effects are handled the way Stripe's docs advise (docs.stripe.com/error-low-level, docs.stripe.com/api/idempotent_requests):
    - Each call creates one `Idempotency-Key` (a UUID). The client's automatic retries (Decision 12) send that same key, so a retry after a timeout never fixes or cancels twice.
    - A `201` stores the returned status (`pending`) on the model. `InvoiceCancelled`, or the status of the fixed record, arrives later by webhook, as with issuing.
    - Answers that need a person come back as a `VerifactuException` with the code: `409 invoice_awaiting_aeat` (try again once AEAT has decided), `409 invoice_cancelled`, and `422` for a correction that changes fiscal data. The app shows the exception's message.
    - An outcome that stays unknown after the retries throws too. The next webhook, or `verifactu:refresh-pending`, settles it. A second click gets a clear `409` instead of a second record.
    - The README tells apps to call both methods after their database transaction commits, as Stripe calls are made. A call inside a transaction that then rolls back would leave the service changed and the app not.
    - `correctOnVerifactu(?string $description = null)` sends only what a fix may change. Without a description, it resends after a technical rejection. Neither method needs a new column.
11. **Events**, each carrying the model (`InvoiceRejected` and `InvoiceAcceptedWithErrors` also carry AEAT's `errorCode` and `errorMessage`, `InvoiceNotIssued` the exception): `InvoiceIssued`, `InvoiceNotIssued`, `InvoiceAccepted`, `InvoiceAcceptedWithErrors` (registered, but needs a fix), `InvoiceRejected`, `InvoiceCancelled` and `InvoiceBatchCompleted`. A status event fires only when the stored status changes.
12. **The facade covers what the apps use** (owner, 2026-11-19): `Verifactu::createInvoice`, `getInvoice`, `listInvoices`, `correctInvoice`, `cancelInvoice`, `createInvoiceBatch`, `getInvoiceBatch`, `listInvoiceBatchItems` and `checkTaxId`. They are named after the API's operations and take and return the API's arrays. The model methods and jobs are built on them.
    - One client class with `Http::baseUrl()->withToken()->acceptJson()->connectTimeout(5)->timeout(30)`. Like Stripe's SDK (`maxNetworkRetries`), every call retries automatically, twice by default (`config('verifactu.retries')`). It retries on a connection error, `429`, any `5xx` (a `500` creates nothing and is never stored against the key, so the docs say to retry it) and `409 idempotency_key_in_progress`, waits the `Retry-After` seconds (one second without the header), and sends the same `Idempotency-Key` on a POST. That makes the retries safe. The list of retryable answers lives in one place, `VerifactuException::isRetryable()`. Direct calls (fix, cancel, reads, commands) use the automatic retries. Queued jobs turn them off and retry through the queue (Decision 6, DEX-001), so a slow service never stacks waits beyond a worker's timeout.
    - `Verifactu::http()` returns that same configured `PendingRequest` (URL, token, timeouts, retries) for the five endpoints the facade leaves out (owner, 2026-11-19). The docs' Laravel tab uses it on those pages, for example `Verifactu::http()->get('exports/xml', ['month' => '2026-11'])`.
    - Errors become `VerifactuException` (`status`, `errorCode`, `message`, `errors`, `retryAfter`). Apps branch on `errorCode`, never on the message.
13. **Tax-ID check**:
    - `Verifactu::checkTaxId($taxId, $name)` returns a `TaxIdCheck` (`result` enum, `officialName`).
    - The validation rule `new KnownToAeat(nameField: 'legal_name')` refuses `not_identified`, `deregistered` and `revoked`, and passes when AEAT can't answer, as the guide does.
14. **`Verifactu::fake()` fakes the service, not the package.**
    - It registers an `Http::fake()` for the configured URL that answers like the service: numbers in order, invoices kept in memory, batches completed at once. The app's tests therefore run the package's real jobs, trait and events.
    - `->decide($model, InvoiceStatus::Rejected, errorCode: '1105')` plays AEAT's answer, as a signed webhook would.
    - Assertions: `assertIssued($model, ?Closure)`, `assertNothingIssued()`, `assertBatchSent()`, `assertCorrected($model)` and `assertCancelled($model)`.
15. **Commands**:
    - `verifactu:install`, a wizard with Laravel Prompts (owner, 2026-11-19: show the lines, don't edit the model):
        1. Publishes the config.
        2. Adds the three keys to `.env` (`VERIFACTU_URL`, `VERIFACTU_TOKEN`, `VERIFACTU_WEBHOOK_SECRET`) and `.env.example` (empty).
        3. Asks which model is the invoice (`search` over `app/Models`).
        4. Asks which existing columns hold the number, date, status and QR code, or whether to create them.
        5. Writes them into the config.
        6. Writes an add-only migration for the missing columns, and publishes the batches migration.
        7. Lists columns it recognises as obsolete (`hash`, `previous_hash`, `sequential`…) without dropping them.
        8. Prints the lines to add to the model, the schedule line and the webhook URL to give an administrator.
    - `verifactu:status`: checks the connection and the token's environment, and counts the app's invoices by status.
    - `verifactu:refresh-pending`, scheduled hourly by the app: refreshes invoices `pending` for over an hour, and applies batches not yet applied.
    - `verifactu:correct {invoice} {--description=}`: the command form of `correctOnVerifactu()`.
    - Commands use Laravel 13's `#[Signature]` and `#[Description]` attributes.
16. **`php artisan about`** shows the service's host, the environment (Test or Live, from the token's `vf_test_`/`vf_prod_` prefix), the invoice model and the webhook URL. It never shows the token or the secret.
17. **Configuration** (`config/verifactu.php`): `url`, `token` and `webhook_secret` come from `.env`. Everything else is fixed in the file, with no `env()`: `model`, `columns`, `exemption_reason`, `webhook_path`, `queue`, `retries` and the timeouts.
