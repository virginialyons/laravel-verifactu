## Review sweep of T1–T9 (2026-11-19, owner's request)

The owner asked for an independent review of T9 and of the whole package, task by task, and for the code to use Laravel's own helpers wherever Laravel 13 has one ("Don't guess, don't produce AI slop... Invoices and AEAT is high stakes"). One `laravel:laravel-simplifier` reviewer per task (T1–T9, review only, a shared brief), a docs agent for Laravel 13's helper reference, and one for AEAT's official "Validaciones y errores" (v1.2.2, 08/04/2026). Every finding was checked in `vendor/` or the docs before it was fixed; the fixes were applied in one pass for consistency; T8's fake was rebuilt by an agent in a copy of the tree and merged back. Owner rules added during the sweep (memory): follow what Laravel and its first-party packages do; give a check an `isX()`/`isNotX()` pair rather than `! isX()`.

Fixed:
- **P1 (T4)**: a database failure after a `201` fired `InvoiceNotIssued` for an invoice AEAT had; the job now releases, and the retry's same key replays the answer.
- **P1 (T8)**: the fake accepted a correction that changes amounts; the service refuses it with `422 correction_changes_fiscal_data`.
- **P2**:
  - `IssueInvoice` reads an invoice back by its reference on `422 idempotency_key_reused` too, as on `409 external_reference_already_used`. An invoice edited between a lost answer and the retry is stored, not reported as not issued (Decision 6). Building the request at dispatch was tried first and reverted after the second review: it froze an invoice before the same transaction saved its lines.
  - The client refuses `http://`, never follows redirects, and turns any answer that isn't a success with the API's envelope into a `VerifactuException`. A redirect also crashed the retry callback with a `TypeError` (`shouldRetry(?Throwable)` now).
  - `ApplyInvoiceBatch`'s lock outlasts its retries, and it reloads the batch.
  - `SendInvoiceBatch::failed()` skips invoices already issued.
